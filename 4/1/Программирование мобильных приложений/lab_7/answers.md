# Лабораторная №7 — SQFLite, File System, изоляты: ответы на вопросы

Все ответы опираются на код проекта и на реальное поведение `path_provider 2.1.6`
(проверено по исходникам пакетов `path_provider_android`, `path_provider_foundation`,
`path_provider_linux`, `path_provider_windows` и на запуске под Android).

---

## 1. Директории, поддерживаемые всеми платформами

Под «всеми платформами» имеются в виду Android, iOS, macOS, Windows и Linux.
Их реализует **5 каталогов** из требуемого списка:

| Каталог | Метод `path_provider` | Android | iOS | macOS | Windows | Linux |
|---|---|---|---|---|---|---|
| Temporary | `getTemporaryDirectory()` | ✅ | ✅ | ✅ | ✅ | ✅ |
| Application Support | `getApplicationSupportDirectory()` | ✅ | ✅ | ✅ | ✅ | ✅ |
| Application Documents | `getApplicationDocumentsDirectory()` | ✅ | ✅ | ✅ | ✅ | ✅ |
| Application Cache | `getApplicationCacheDirectory()` | ✅ | ✅ | ✅ | ✅ | ✅ |
| Downloads | `getDownloadsDirectory()` | ✅ | ✅ | ✅ | ✅ | ✅ |

Уточнения по реализациям:

- **Temporary** — на Android это `Context.getCacheDir()`, на iOS/macOS — `NSCachesDirectory`,
  на Linux — `$TMPDIR` (по умолчанию `/tmp`), на Windows — `GetTempPath`.
- **Application Support** — на Android `Context.getFilesDir()`, на iOS/macOS —
  `NSApplicationSupportDirectory`, на Linux — `$XDG_DATA_HOME/<id приложения>`,
  на Windows — `RoamingAppData`.
- **Application Documents** — на Android `Context.getDir("flutter", MODE_PRIVATE)`,
  на iOS/macOS — `NSDocumentDirectory`, на Linux — XDG-каталог `DOCUMENTS`
  (может быть `null`, если `xdg-user-dir` не установлен).
- **Application Cache** — на Android `Context.getCacheDir()`, на iOS/macOS —
  `NSCachesDirectory`, на Linux — `$XDG_CACHE_HOME/<id>`, на Windows — `LocalAppData`.
- **Downloads** — на Android `Environment.DIRECTORY_DOWNLOADS`, на iOS/macOS —
  `NSDownloadsDirectory`, на Windows — `KnownFolder.Downloads`, на Linux — XDG-каталог
  `DOWNLOAD` (тоже может быть `null`).

Итого из 9 требуемых каталогов «универсальных» — **5**, а не «каталог Application Library»
(он только iOS/macOS) и не «External *» (только Android).

В коде это зафиксировано в `lib/services/directory_service.dart` →
таблица `DirectoryService.specs` (у каждого каталога свой список `supported`).

## 2. Директории, поддерживаемые только на Android

Их **три**, и все они связаны с внешним хранилищем:

| Каталог | Метод `path_provider` | Реализация на Android |
|---|---|---|
| External Storage | `getExternalStorageDirectory()` | `Context.getExternalFilesDir(null)` — «внешняя» папка приложения |
| External Cache Directories | `getExternalCacheDirectories()` | `Context.getExternalCacheDirs()` — список (внешняя SD-карта + основное хранилище) |
| External Storage Directories | `getExternalStorageDirectories()` | `Context.getExternalFilesDirs(type)` — список по типам `StorageDirectory` (music, downloads, dcim, documents, ...) |

На iOS/macOS эти методы выбрасывают `UnsupportedError`
(«getExternalStoragePath is not supported on this platform»): в песочнице iOS
доступ к «внешнему» хранилищу запрещён, аналога `getExternalFilesDir` нет.
На Windows и Linux их тоже нет.

Дополнительно: **Application Library** (`getLibraryDirectory()`) на Android
не поддерживается вообще — метод доступен только на iOS/macOS
(`NSLibraryDirectory`), а на Android `MethodChannelPathProvider` явно бросает
`UnsupportedError('Functionality only available on iOS/macOS')`.

## 4. SQLite: преимущества и недостатки

**SQLite** — встроенная реляционная СУБД, хранящая данные в одном файле
(в проекте — `games.db` в `getDatabasesPath()`), доступная через пакет `sqflite`.

### Преимущества

1. **Не требует сервера и сети** — база лежит на устройстве, приложение работает офлайн.
2. **Транзакции и ACID** — целостность данных: `insert/update/delete` можно оборачивать
   в `db.transaction(...)`, при ошибке изменения откатываются.
3. **SQL-запросы** — сортировка, фильтрация, `LIKE`-поиск, `JOIN`, индексы; не нужно
   вручную реализовывать поиск и сортировку в памяти.
4. **Эффективность** — запросы выполняются не в главном потоке (в `sqflite` БД живёт
   в отдельном потоке/изоляте), чтение большой таблицы не тормозит UI.
5. **Компактность и переносимость** — один файл, стандартный формат, база переносится
   между устройствами и версиями приложения.
6. **Низкий порог входа** — стандартный SQL, нет необходимости в ORM.

### Недостатки

1. **Ограниченные типы и возможности** — нет полноценных `DATE`, `BOOLEAN`,
   пользовательских функций; слабая поддержка `ALTER TABLE` (нужно пересоздавать таблицу).
2. **Синхронный доступ к API из UI-потока** — запросы выполняются в фоновом потоке,
   но `await` всё равно нужен; при большом объёме данных нужен `compute()`/`Isolate`.
3. **Целочисленный `id` и приведение типов** — `year` приходится приводить к `TEXT`
   для поиска через `CAST(year AS TEXT) LIKE ?`.
4. **Нет шифрования «из коробки»** — для чувствительных данных нужно дополнительно
   использовать SQLCipher.
5. **Миграции требуют внимания** — при изменении схемы нужен `onUpgrade` с номером версии.
6. **Не подходит для очень больших объёмов и сложных связей** — предпочтительнее
   специализированные хранилища (Hive, Isar, Drift, ObjectBox).

## 5. Библиотеки для доступа к файловой системе. Можно ли обойтись без `path_provider`?

### Используемые библиотеки

- **`path_provider`** — кроссплатформенный способ узнать пути к системным каталогам
  (все 9 каталогов из задания берутся отсюда).
- **`dart:io`** — низкоуровневый API: `File` (чтение/запись/размер), `Directory`
  (создание, листинг), `FileStat` (размер, дата изменения), `Platform` (текущая ОС).
- **`path`** — вспомогательная сборка путей (`p.join(...)`), чтобы не зависеть от
  разделителей каталогов.

### Можно ли обойтись без `path_provider`?

**Да, но дороже.** Альтернативы:

1. **Вручную через `dart:io` + свои пути** — например, `Directory.systemTemp`
   (аналог Temporary). Но «правильные» каталоги приложения (files, cache, documents)
   задаются ОС, и без плагина их пути придётся либо хардкодить (ломается после
   обновления/смены пакета), либо получать через нативные каналы вручную.
2. **Своя нативная реализация через MethodChannel** — на Android вызвать
   `Context.getFilesDir()`, `getCacheDir()`, `getExternalFilesDirs()`; на iOS —
   `FileManager.default.urls(for: .applicationSupportDirectory, .documentDirectory, .cachesDirectory)`.
   Это ровно то, что делает `path_provider` внутри, только поддержку платформ,
   тесты и обработку ошибок придётся написать самому.
3. **Сторонние пакеты** — `shared_preferences` (для настроек, не для произвольных файлов),
   `open_filex`/`file_picker` (не то же самое), `flutter_file_dialog`.

Вывод: `path_provider` — стандартное и рекомендуемое решение; отказ от него
оправдан только при необходимости в каталоге, который `path_provider` не покрывает
(например, произвольный путь «Downloads» с ручным выбором пользователя).

В проекте `path_provider` используется в `lib/services/directory_service.dart`,
а работа с файлами — в `lib/services/file_service.dart` (`dart:io`).

## 6. Библиотеки для работы с изолятами. Встроены ли они в Dart?

**Да, механизм изолятов встроен в Dart** — отдельные пакеты не нужны:

- **`dart:isolate`** (часть SDK):
  - `Isolate.spawn(entryPoint, message)` — создание изолята вручную;
  - `Isolate.run(callback)` — «одноразовый» изолят (Dart 2.19+), заменяет `compute`;
  - `SendPort` / `ReceivePort` — каналы обмена сообщениями;
  - `TransferableTypedData` — передача больших буферов без копирования;
  - `Isolate.current`, `Isolate.exit`, `Capability`.
- **`flutter/foundation`** — `compute<Q, R>(callback, message)`: удобная обёртка над
  `Isolate.spawn`, которая сама создаёт и убивает изолят и возвращает `Future<R>`.

В проекте используются оба варианта: `compute()` — в `lib/services/isolate_service.dart`
(функция `_task`), `Isolate.spawn` — там же (функция `_spawnEntryPoint`
с обменом через `SendPort`/`ReceivePort`).

## 7. Зачем нужны изоляты? Что произойдёт при тяжёлой операции в main isolate?

### Зачем

1. **Параллелизм** — тяжёлое вычисление (парсинг JSON, сжатие, обработка изображений,
   обход дерева каталогов) идёт одновременно с отрисовкой UI.
2. **Отзывчивость интерфейса** — главный изолят отвечает за кадры; 60 fps требует
   укладываться в ~16 мс на кадр.
3. **Изоляция состояния** — у изолята своя память и своя копия глобальных переменных;
   гонки данных и случайные ошибки в одном изоляте не ломают другой.
4. **Защита UI от исключений** — падение в изоляте можно перехватить (`onError`,
   `try/catch` в `Future`), тогда как исключение в main isolate уронит приложение.
5. **Фоновые задачи** — синхронизация с сетью, вычисления, обработка файлов.

### Что произойдёт при тяжёлой операции в main isolate

- **Фриз интерфейса**: пока изолят занят, он не обрабатывает кадры — анимации
  замирают, кнопки не реагируют, `ScrollView` не скроллится.
- **Счётчик кадров падает** — Flutter не может отрисовать следующий кадр,
  «пропускаются» кадры (jank), при длительной операции — «всё застыло».
- **ANR (Application Not Responding)**: если главный поток Android заблокирован
  более ~5 секунд, система показывает диалог «Приложение не отвечает».
- **Watchdog-kill**: Android может убить процесс, если main isolate не отвечает.
- **Ошибки в UI**: любой `throw` в main isolate приводит к «серому экрану»/крашу.

Именно это демонстрируется на экране «Изоляты»: запись и чтение файла выполняются
в отдельном изоляте, а экран остаётся отзывчивым — результат операции появляется
только после её завершения, главный изолят при этом не выполняет файловую работу.

## 8. Чем `compute()` отличается от `Isolate.spawn()`? Когда что использовать?

| | `compute()` | `Isolate.spawn()` |
|---|---|---|
| Уровень API | Высокий, «одной строкой» | Низкий, ручное управление |
| Аргументы | Один `message` + один результат | Любое отправляемое сообщение, включая `SendPort` |
| Результат | `Future<R>` — один ответ | Любое число сообщений через порты |
| Жизненный цикл | Изолят создаётся и **убивается** автоматически | Изолят живёт, пока его не убьют (нужен `kill`/`Isolate.exit`) |
| Обработка ошибок | Через `try/catch` в `Future` | `onError`, `onExit`, `errorsAreFatal` |
| Идентификатор | Не виден | `Isolate.current.hashCode`, `debugName` доступны |
| Обмен в процессе | Нет (fire-and-forget) | Да, двусторонний обмен через `SendPort`/`ReceivePort` |
| Под капотом | `Isolate.spawn` + ожидание результата | — |

Под капотом `compute()` — это тот же `Isolate.spawn`: Flutter создаёт изолят,
передаёт ему `message`, запускает callback и возвращает результат через порт,
после чего изолят закрывается.

**Когда что использовать:**

- **`compute()`** — разовая тяжёлая задача без промежуточных результатов:
  парсинг большого JSON, подсчёт, сортировка в памяти, чтение/разбор файла,
  запись сериализованных данных. В коде лабораторной — запись и чтение файла
  (`_task`).
- **`Isolate.spawn()`** — долгоживущая фоновая задача, потоковая обработка,
  обмен сообщениями в обе стороны, несколько портов, необходимость отмены
  изолята или отслеживания его завершения. В коде лабораторной — запись и
  чтение файла через `SendPort`/`ReceivePort` (`_spawnEntryPoint`).

## 9. Какие данные можно передавать между изолятами, а какие нельзя?

### Можно

- `null`, `bool`, `int`, `double`, `String`;
- списки и карты (`List`, `Map`), состоящие только из перечисленных выше значений;
- `SendPort`, `ReceivePort`, `Capability` (каналы связи);
- `TransferableTypedData` — большие буферы (`TypedData`), которые передаются
  **без копирования** (zero-copy);
- простые объекты/записи, если они приведены к отправляемому виду
  (например, `Map<String, Object?>` вместо экземпляра класса).

Важно: при отправке через `SendPort` данные **копируются** — они не разделяют память
с исходным изолятом (кроме `TransferableTypedData`).

### Нельзя

- **Экземпляры произвольных классов** (`GameRecord`, `ComputerGame` и т. п.) —
  изолят получает не тот же объект, а копию примитивов; нужно сериализовать
  в `Map`/JSON и собрать заново на другой стороне;
- **замыкания и callback-и** (`Function`, анонимные функции);
- **UI-объекты Flutter**: `BuildContext`, `Widget`, `State`, `TextEditingController`,
  `ThemeData`, `ScaffoldState` и любые объекты, привязанные к main isolate;
- **объекты плагинов и ресурсы ОС**: `Database` из `sqflite`, экземпляры
  `path_provider`, `File`/`Socket` (неизменяемый дескриптор файла),
  дескрипторы, соединения;
- **изменяемое общее состояние** — глобальные переменные не разделяются между
  изолятами, каждый изолят имеет свою копию (это и плюс, и причина «неожиданных»
  значений при попытке использовать глобальный счётчик).

Практический вывод: между изолятами передают **данные** (`Map`, `JSON`, примитивы),
а не **объекты**; для обмена используют `SendPort`/`ReceivePort`.

В лабораторной данные сущности в изоляты передаются как
`Map<String, Object?>` (ключ, путь, содержимое файла), а обратно возвращается
`Map<String, Object?>` с результатом операции (размер и контрольная сумма).

## 10. Как производилась обработка ошибок в зависимости от платформы?

Обработка реализована в `lib/services/directory_service.dart` (`DirectoryService.resolve`).

### 1. Матрица поддержки платформ

Для каждого из 9 каталогов зафиксированы поддерживаемые платформы
(`DirectoryService.specs` → `DirectorySpec.supported`). Текущая платформа определяется через
`defaultTargetPlatform` (`Android`, `iOS`, `macOS`, `Windows`, `Linux`),
список неподдерживаемых — как разность «все платформы − поддерживаемые»
(`DirectoryService.unsupportedPlatformsOf`).

### 2. Перехват типичных исключений `path_provider`

| Исключение | Когда возникает | Пример |
|---|---|---|
| `MissingPlatformDirectoryException` | система не смогла вернуть путь (вернулся `null`) | `getDownloadsDirectory()` на Linux без `xdg-user-dir` |
| `UnsupportedError` | метода нет на этой платформе | `getLibraryDirectory()` на Android, `getExternalStorageDirectory()` на iOS/macOS |
| любое другое `Exception` | непредвиденная ошибка плагина | сбой метода канала |

### 3. Формат сообщения об ошибке

Ошибка выводится пользователю и **содержит конкретные неподдерживаемые платформы**:

```
Каталог «Application Library» недоступен на платформе Android:
Functionality only available on iOS/macOS.
Не поддерживаются платформы: Android, Windows, Linux.
Поддерживаются платформы: iOS, macOS.
```

То есть в сообщении есть: текущая платформа, исходная причина из плагина,
список неподдерживаемых платформ и список поддерживаемых.

### 4. Поведение интерфейса

- На экране «Файлы» у неподдерживаемых каталогов кнопки «Записать» и «Прочитать»
  **заблокированы** (`onPressed: null` — серый фон), вместо пути выводится текст
  ошибки с перечислением неподдерживаемых платформ.
- Поддерживаемые каталоги показывают абсолютный путь (для `getExternalCacheDirectories()`
  и `getExternalStorageDirectories()` — список путей), кнопки активны.
- Операции записи/чтения дополнительно оборачиваются в `try/catch`
  (`FileService`), ошибка выводится строкой статуса вверху экрана.

Проверка этой логики автоматизирована: тест
`Файловая система определяет каталоги платформы и сообщает о неподдерживаемых`
в `integration_test/app_test.dart` требует, чтобы для каждого недоступного
каталога сообщение содержало строку `«Не поддерживаются платформы»`.
